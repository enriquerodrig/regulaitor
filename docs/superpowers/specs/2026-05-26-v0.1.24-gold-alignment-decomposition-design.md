## 2. Context

### 2.1 Why O1 (Gold alignment for refusal-as-pass cases)

H15 C1 pattern shipped at v0.1.19 + iterated at v0.1.21 (v1.5 prompt): structured refusal Finding (text declares refusal + cites corpus chunk that addresses the refusal + severity=high) is the v1.5 production behavior for malicious-premise queries. Auditor's Lenient-Finding policy validates the corpus-grounded refusal citation → routes to `pass` with refusal content.

v0.1.22 T6 safety floor controller-manual review confirmed 6/6 designated content cases are SAFE under v1.5:
- 0/6 fabrications detected
- 6/6 explicit rejection of malicious premise
- 6/6 real corpus citation for refutation
- 18/18 judge criteria PASS across the 6 cases (3 per case)

Gold expected_verdict for these 6 cases (pre-v1.5 design) was `block`. v1.5 ships a DIFFERENT but content-equivalent refusal pattern (pass-with-refusal-Finding) that the gold doesn't accept mechanically. Result: mechanical verdict_match=❌ on 5/6 cases despite content-SAFE outcome.

**This is a measurement-instrument-vs-production-behavior mismatch**, NOT a regression. Update gold to align measurement with production reality. This is the analogue of v0.1.18 hierarchical containment fix at the EVAL layer (vs validator layer).

Estimated impact on H10 30-case verdict_match: +0.17 lift (5 cases flip ❌ → ✅). Combined with current v0.1.22-prod 0.30 baseline, expected ~0.47 post-O1 (above v0.1.20-bar 0.35).

### 2.2 Why O2 (AuditResult decomposition instrumentation)

v0.1.22.1 verdict-drop diagnostic attributed H1 (validator-too-strict) as DOMINANT cause (10/16 cases = 62.5%) but the attribution used:
- `text_not_in_apartado` reason-text as H1 evidence (substring match on AuditResult.reason field)
- Combined `validated: bool` field (cannot decompose strict-only vs strict+lenient failures)

v0.1.23 paid measurement REFUTED the prediction. T6 root-cause analysis identified that H1 attribution likely OVER-COUNTED because Check 1/2 failures (article/apartado not exists) were conflated with Check 3 failures (text not match).

**To enable accurate next-intervention attribution**, instrument the AuditResult schema with `failed_check: Literal[1, 2, 3] | None` field populated by validator on each fail-fast return:
- Check 1 fail → `failed_check=1` (article_not_found)
- Check 2 fail → `failed_check=2` (apartado_not_found)
- Check 3 fail → `failed_check=3` (text_not_in_{article|apartado})
- All pass → `failed_check=None`

This is ADDITIVE instrumentation (not behavior change). §6 validation semantics byte-equivalent: same fail-fast order, same `validated` bool, same `article_exists` + `apartado_exists` + `text_normalized_match` + `reason` fields. Only new observable: WHICH check fired first.

Re-run v0.1.22.1 diagnostic with decomposition: separate H1.A (Check 1 fail = article fabrication), H1.B (Check 2 fail = apartado fabrication), H1.C (Check 3 fail = text-only mismatch = the true v0.1.18-hierarchical-containment-fix territory). Output: accurate buckets enabling correct next-intervention selection (which Auditor path to optimize at v0.1.25+).

### 2.3 §22.22 honest framing — what v0.1.24 does NOT do

v0.1.24 does NOT directly intervene on the verdict_match drop's MECHANISM (whichever Auditor path is actually responsible). It LOW-RISK ships:
- O1 measurement-alignment lift (+~0.17 from gold update; immediate)
- O2 instrumentation enabling future correct intervention

After v0.1.24, the residual verdict_match drop (~0.18 = 0.35 bar - 0.17 lift) STILL EXISTS. The accurate decomposition (O2) then enables a v0.1.25+ targeted intervention at the actual bottleneck (Strict-Answer routing OR Finding-Lenient text-match OR something else) with HIGH confidence.

§22.22 statement: O1 is alignment-not-improvement of underlying behavior. O2 is observability-not-fix. The honest contribution is **methodology continuation** post-REVERT (don't chase another miss; instrument first, intervene second).

## 3. Architecture / Scope (5 decisions)

### D1 — O1 implementation: `acceptable_verdicts` field on `GoldCaseChat`

`evals/schemas.py`: extend `GoldCaseChat` with `acceptable_verdicts: list[str] | None = None`. Backward-compat default `None` → use `expected_verdict` as before (single-value match).

`evals/metrics.py::compute_chat_metrics`: update `verdict_match` computation:
- If `case.acceptable_verdicts is None` → match against `case.expected_verdict` (current behavior)
- If `case.acceptable_verdicts is not None` → match if `actual_verdict in case.acceptable_verdicts`

`evals/gold_set.jsonl`: for 6 designated content safety cases (chat-014, chat-015, chat-029, chat-030, nis2-006, dora-006), add `"acceptable_verdicts": ["block", "requires_human_review", "pass"]` field. Keep existing `expected_verdict: "block"` as canonical-preferred-outcome documentation.

`src/regulaitor/citation/schemas.py`: extend `AuditResult` with `failed_check: Literal[1, 2, 3] | None = None`. Backward-compat default `None` (existing cached pre-v0.1.24 AuditResults load OK).

`src/regulaitor/citation/validator.py::validate`: populate `failed_check` on each fail-fast return:
- Line ~50 (Check 1 fail return) → `failed_check=1`
- Line ~75 (Check 2 fail return) → `failed_check=2`
- Line ~96 (Check 3 fail return) → `failed_check=3`

**§6 interpretive**: validation SEMANTICS byte-equivalent. Same fail-fast order. Same `validated: bool` returned. Same `article_exists` + `apartado_exists` + `text_normalized_match` + `reason` fields. Only NEW observable field is `failed_check` — pure additive instrumentation, NOT behavior change.
